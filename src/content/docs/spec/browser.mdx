<span class="status status--decided">decided</span> in direction ([decision 26](/discussion/decisions/#26-the-browser-is-the-muppets-client)), <span class="status status--draft">draft</span> in detail.

A browser doesn't need a client-side framework to take part in an XTXP session. It already has the three things a client needs, built in:

| The client needs to | The browser does it with | So the muppet sends |
| --- | --- | --- |
| **change the document** | [declarative partial updates](#declarative-partial-updates-change-the-document) | HTML patches aimed at named parts of the page |
| **show what changed** | [CSS view transitions](#view-transitions-make-each-change-visible) | stable names for every node |
| **take input on an element** | [popovers with anchor positioning](#popovers-carry-the-control-handles) | a handle for every selectable element |

Put together, **the browser itself is the muppet's client**. Patches go in, transitions show the change, popovers handle input, and almost no JavaScript sits in between. The muppet does all the CRDT work, exactly as [decision 2](/discussion/decisions/#2-the-no-js-client-is-a-puppet) says; what changes is that the browser stops being a page that reloads and becomes a live view, applying the muppet's patches with its own HTML parser.

This idea comes from Schalk Venter's talk [*Surprise, it's server rendering*](https://za.pycon.org/talks/4-suprise-its-server-rendering/) (see [North star](/overview/north-star/#surprise-its-server-rendering)). The talk named these features as ways to make server-rendered sites feel live. For XTXP they are more than that: they are the client.

## Declarative partial updates change the document

<span class="status status--draft">draft</span>

[Declarative partial updates](https://developer.chrome.com/docs/web-platform/declarative-partial-updates) let a page mark places in its HTML with processing instructions, and let later HTML replace what's there with a `<template for>`. The browser's parser applies the patch itself, as the HTML arrives.

**HTML patches are the wire format to the browser.** When the muppet renders a document, it marks every node it may need to replace, named from the node's [node ID](/overview/glossary/):

```html
<?start name="n7-12">
  <rect id="sun" x="40" y="40" width="80" height="80" fill="gold"
        style="view-transition-name: sun; anchor-name: --n7-12"/>
<?end>
```

When that node changes, whoever changed it, the muppet sends only its new rendering:

```html
<template for="n7-12">
  <?start name="n7-12">
    <rect id="sun" x="48" y="40" width="80" height="80" fill="gold"
          style="view-transition-name: sun; anchor-name: --n7-12"/>
  <?end>
</template>
```

The template repeats the marker, so the same node can be patched again. A Yrs update never reaches the browser, and the browser never runs Xmesh: the muppet integrates operations, works out which nodes they touched, and renders just those.

### The patch stream

**The page's own response stays open.** After the first render, the muppet keeps the HTTP response open and flushes a `<template for>` each time the session changes. With no `fetch`, no polling and no script, the page stays live. The stream is an enhancement for modern browsers, not a replacement: the `<meta http-equiv="refresh">` and `304 Not Modified` loop of the [no-JS edit loop](/spec/addressing/#the-no-js-edit-loop) stays the baseline that works in every browser, older ones included, and the patch stream is what makes it sing where the browser can do it.

Templates are streamed as children of `<body>`, which lets them reach markers anywhere in the document.

### Edits still go in as forms

**Edits stay [form POSTs](/spec/addressing/#forms)**, each naming its node, the snapshot it was rendered from and a CSRF token, plus a request ID of the page's own.

### The answer confirms where the edit landed

A POST is a request, not a fact. The muppet may place an edit somewhere other than where it was aimed: an editor snaps a shape to the grid or to another shape, a game world applies its rules (collisions, turns, positions that are taken), a stale edit is rebased onto a newer state, or the grant doesn't allow it at all. So the answer to every POST is a **confirmation**: what the edit became, rendered.

- **The confirmation is a patch.** It carries the node as the muppet resolved it (the snapped position, the move the game allowed) and a short status region saying what happened, such as "Moved to 48, 40, snapped to the grid" or "Not allowed: that square is taken". The request ID ties it to the POST that caused it.
- **With a patch stream, a no-JS browser gets it on the stream.** A form POST can't patch the page it came from without navigating, so the muppet answers **`204 No Content`**, the browser stays on the page, and the confirmation is the next patch on that page's stream, sent to it ahead of the same change reaching anyone else. A [view transition](#view-transitions-make-each-change-visible) shows the shape settling where it landed.
- **A page with script can take it as the response.** The Wasm muppet, or a few lines of script, can send the form with `fetch` and apply the response body, the same confirmation patch, with `streamHTML`.
- **On the baseline loop it's the redirect.** The `303` lands on the page as it now stands, with the status region filled in.

One renderer produces every change, the user's own included; the confirmation is that renderer's answer to one request.

### Coarse or fine patches

- **Per node** (the default): a marker around every node the muppet may patch, as above. The smallest patches, and the closest match to the operations that caused them.
- **Per region:** replace a whole region, such as a layer, and let [view transitions](#view-transitions-make-each-change-visible) match old nodes to new ones by name. Simpler to render, and enough for small documents.

Both are the same mechanism; a muppet can mix them.

## View transitions make each change visible

<span class="status status--draft">draft</span>

A patch that simply swaps one rendering for another makes edits from other people hard to follow: something on the canvas jumps, and you have to work out what. With [CSS view transitions](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API), every patch becomes a change a person can **watch happen**: the shape slides to its new place, the colour fades across, a new element grows in, a deleted one fades out.

**Every rendered node gets a stable `view-transition-name`**, so the browser can pair its old and new renderings. The name comes from the element's own `id` where it has one, since [v1 moves](/spec/math/) replace a node with a copy and give it a new node ID, and from its node ID otherwise.

**Changes are styled by who made them.** A `view-transition-class` says whose change it is (yours, another person's, an agent's), so CSS can animate each differently: your own edits settle quickly, and others' are slower and highlighted in their author's colour, the same colour the [redline](/spec/views/) uses.

### Agents and peers you can follow

This matters most for edits you didn't make. An **agent** is just another peer with a key: its edits arrive through the host like anyone's, become patches like anyone's, and animate like anyone's. Watching an agent move, recolour and add things on the canvas is what makes its work easy to follow, check and trust, rather than a document that silently changed under you.

### Navigations animate too

On the baseline form, redirect and GET loop, cross-document view transitions (`@view-transition { navigation: auto; }` in CSS) animate from the old page to the new one, with the same names and the same author styling. The baseline looks like the live version, only less often.

## Popovers carry the control handles

<span class="status status--draft">draft</span>

To edit an element, a person needs handles on it: move, recolour, delete, edit an attribute. The [popover API](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API) with [CSS anchor positioning](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_anchor_positioning) gives every element its handles declaratively. The element names itself as an anchor (`anchor-name: --n7-12`, as in the patch above), and its handle attaches to it:

```html
<button popovertarget="h-n7-12" class="select" style="position-anchor: --n7-12">
  Select sun
</button>
<div id="h-n7-12" popover style="position-anchor: --n7-12">
  <form method="post"> … nudge, recolour, delete … </form>
</div>
```

- **The handles are the M2 forms**, from [decision 23](/discussion/decisions/#23-the-m2-contracts-inkscape-no-js-editing-rendering-safety), put where the user's eyes are: attached to the element, not in a list beside the canvas.
- **They live in the top layer**, so they're never clipped by the drawing's `viewBox` or hidden behind other shapes, and they need no positioning code.
- **Selecting is local.** Opening a handle is the browser's own state, with no request to the host. Like every [view](/spec/views/), it never changes the session. Light dismiss and one-open-at-a-time come free with `popover="auto"`.
- **Handles are patched with their element.** When a node changes, its handle popover comes in the same patch, so a handle never offers to edit a stale version.

The select control is itself anchored over its element, sized to it with `anchor-size()`, so clicking a shape is clicking its button.

## Where the browser stops and the muppet starts

| | Browser | muppet |
| --- | --- | --- |
| CRDT state, merging, grants | | ✓ |
| Rendering nodes to HTML and SVG | | ✓ |
| Applying patches to the page | ✓ (its parser) | |
| Animating changes | ✓ (view transitions) | names and classes |
| Selection and handles | ✓ (popovers) | renders them |
| Turning an edit into operations | sends a form | ✓ |

The same split holds wherever the muppet runs:

- **Server-side, for a browser with no JavaScript:** the patches travel in the page's own HTTP response.
- **In the page, as a Wasm muppet ([M3](/build/milestones/#m3--inkscape-plus-wasm)):** the muppet renders the same HTML patches and applies them with the browser's own HTML setters (`setHTML`, `streamHTML`), inside `document.startViewTransition()`. No virtual DOM or hand-written DOM code: both muppets share one renderer, and the no-JS view and the Wasm view can't drift apart.
- **In a browser that speaks XTXP ([north star](/overview/north-star/)):** the browser's own muppet has a native way to change the document already.

## Support today

<Aside type="caution" title="Chromium first">
Declarative partial updates are new. `<template for>` ships in Chrome and Edge 150; the streaming HTML setters are behind a flag, planned for Chrome 155. Firefox and Safari support neither yet. View transitions and popovers are more widely available; anchor positioning is newer.
</Aside>

"Does this still work with no JS?" stays the test. The meta refresh loop is the baseline every browser gets, and each feature above is a progressive enhancement layered on it:

| Browser | Changes arrive by | Feels like |
| --- | --- | --- |
| **Every browser** (the baseline) | form POST, `303` redirect, GET, and meta refresh with ETags | page by page, animated where cross-document view transitions are supported |
| **Modern browsers with declarative partial updates** (the enhancement) | the patch stream | live, animated |

Handles work the same way: the plain forms are the baseline, and popovers with anchor positioning put them on the element where the browser supports it. Nobody gets a different document, only more or less on screen.

## Still open

The platform is close. The first three gaps below are browser gaps, each expected to need a small polyfill now, against the first-class browser support it points to, in the same spirit as the Wasm muppet polyfilling a browser that doesn't speak XTXP yet ([decision 24](/discussion/decisions/#24-north-star-the-read-write-web-with-xtxp-in-the-browser)). A polyfill is a few lines of script, never a framework, and it goes away as browsers catch up; pages without it still work on the baseline.

- **Does a streamed patch start a view transition on its own?** Today a same-document view transition is started from script, with `document.startViewTransition()`. **Probed in Chromium 158: it doesn't.** A streamed `<template for>` patch applies instantly, so that one call is the near-zero JavaScript an animated stream needs ([M2-y-sweet report](/build/m1-y-sweet-report/#the-browser-m2-y-sweet-part-a)).
- **SVG.** Probed in Chromium 158: markers inside inline `<svg>` are found, but a `<template for>` patch's content is parsed in an HTML context, so a replacement SVG element comes out in the HTML namespace and never draws. Natively, SVG can only be patched by region (the whole `<svg>`); per-element patches need contextual parsing, as the WebSocket polyfill does. SVG child elements also don't get their own view transition groups in Chromium 158 or 141, so a change inside a drawing cross-fades the whole `<svg>`. Still open: anchors on SVG elements, and whether an HTML layer over the drawing is the answer for per-element animation and handles.
- **Knowing when to stream.** Without script, a host can't feature-detect `<template for>`, and a browser that ignores it would sit on a page that never finishes loading. Client hints, an explicit "live" link, or something else.
- **Rendering safety.** Patches carry rendered user content into the page, so the [rendering-safety](/spec/addressing/#rendering-safety) questions apply to every patch, not just the first page.
- **Awareness.** Whether other people's open handles and selections are shown, as [awareness](/spec/wire/#messages) patched into the page.
