The Wire half of XTXP defines how operations get from one node to another. It runs over **XMPP**, borrowing the practices that make the Conversations mobile client reliable on patchy connections.

## Why XMPP

- **Federated identity.** A participant is `user@domain`, and any domain can host a server.
- **Rooms with presence.** A document session is a multi-user chat room (XEP-0045). Presence says who is in the drawing; message stanzas carry operations.
- **An ordered archive.** Message Archive Management (XEP-0313) lets a late joiner or reconnecting phone fetch exactly what it missed.
- **Chat and drawing share a channel.** Comments are nodes in the document tree, so they merge like any other edit, and they can be mirrored as ordinary room messages for chat-only clients.

## The patch envelope

<span class="status status--open">open</span>

Operations travel as XML inside XML stanzas, which is where an earlier attempt went wrong (see [Inkboard](/discussion/prior-art/#inkboard-and-pedro)). The envelope needs:

- **its own namespace**
- **an encoding that survives transit** without servers or clients reformatting the payload
- **a fallback `<body/>`** so clients that don't understand XTXP show something sensible, or nothing, rather than raw XML
- **branch routing**: which branch an operation belongs to

## Binding to `xtxp://`

<span class="status status--open">open</span>

Not yet decided: does an `xtxp://host/path` address resolve to an XMPP room (the way `xmpp:` URIs do, RFC 5122), or does XTXP get its own socket binding alongside XMPP? See [Addressing](/spec/addressing/).

<Aside type="tip">
Encryption: rooms can use transport encryption only, or end-to-end encryption (OMEMO). In an E2E room the server is a blind relay, and a server-side MUPPET can still take part as one of the user's own devices.
</Aside>
