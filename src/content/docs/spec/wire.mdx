The Wire half of XTXP defines how operations get from one node to another. It is a small sync protocol that doesn't depend on any one transport, plus a few **bindings** that carry it.

## What the core needs from a transport

Very little. Xmesh operations can be applied in any order, and applying one twice does no harm. So a transport only has to deliver operations **eventually, at least once, in any order**. It doesn't need ordering guarantees, exactly-once delivery or a durable message queue.

Recovering from a dropped connection is part of XTXP itself, not something borrowed from the transport:

## Messages

<span class="status status--draft">draft</span>

The sync messages follow the [Yjs sync protocol](/discussion/prior-art/#the-yjs-sync-protocol), and operations travel in Yrs's binary update format. XTXP adds its own messages for identity and access alongside them.

| Message | Purpose | Stored? |
| --- | --- | --- |
| `hello` / `challenge` / `prove` | Authenticate a connection by public key. See [Identity and access](/spec/identity/). | No |
| `bind` | Signed: "public key P owns client ID 7 on this document." | Yes |
| `sync-1` | "Here is my state vector." | No |
| `sync-2` | "Here are the operations you're missing." | Yes, as operations |
| `update` | New operations, as they happen. | Yes |
| `grant` / `revoke` | Signed changes to who may read or write a session. | Yes |
| `awareness` | Cursors, selections, presence. Fire-and-forget, overwritten, never archived. | No |

Cursors and presence travel separately from operations. A 60 Hz cursor stream should never be archived, wrapped in anything heavy, or replayed to a late joiner.

## Bindings

| Binding | Used by | Notes |
| --- | --- | --- |
| **WebSocket**, binary frames | Wasm MUPPETs in the browser, the Inkscape fork, CLI peers | The primary binding, chosen for raw speed. Hosts serve it directly. |
| **HTTP** forms and redirects | Browsers with no JavaScript, through a server-side MUPPET | See [Addressing](/spec/addressing/#the-no-js-edit-loop). |
| **XMPP**, through a bridge | Mobile and chat clients such as Conversations, and federation | A bridge in front of a host, not the core transport. |

## The XMPP bridge

XMPP is good at things a browser tab isn't: holding messages while a phone sleeps, waking it with a push, and fitting into chat apps people already use. The bridge keeps those strengths for the clients that need them:

- **XEP-0198** stream management and **XEP-0313** message archive for flaky mobile links
- **XEP-0352** client state and **XEP-0357** push, to save battery
- **chat interop**: canvas comments mirrored as room messages, and replies turned back into comments ([open question 7](/discussion/open-questions/#q7-what-does-a-conversations-user-get-in-m4))
- **OMEMO** end-to-end encryption for rooms that want it

Behind the bridge, everything is ordinary XTXP to a host. Inkboard's old problem of XML getting damaged inside XMPP stanzas is now one bridge's concern, not the core wire format's (see [prior art](/discussion/prior-art/#inkboard-and-pedro)).

## Encryption

Every binding runs over TLS. A session can also be end-to-end encrypted, so that its host only sees ciphertext. The host can still **admit** operations, because client bindings and grants are metadata it can check. It can't compact the session into a full state or render previews, though, so those move to the clients. A server-side MUPPET can still take part as one of the user's own devices.

## Still open

- How XTXP's own messages (identity, grants) are framed alongside the Yjs sync messages.
- Whether `xtxp://` names the WebSocket binding directly, or resolves to it through a muppet disco.
- How the XMPP bridge is built: for example as a component plugged into an existing XMPP server, speaking XTXP to a host.
