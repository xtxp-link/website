The Math half of XTXP defines what every implementation of Xmesh must compute. Implementations are free in *how* they compute it. They must agree on *what* comes out, down to the [SHA-256 of the canonical XML](/build/verification/).

## Requirements

1. **Convergence.** Peers that have seen the same set of operations hold the same document, whatever order those operations arrived in.
2. **Intent preservation.** An attribute change and a concurrent child insertion on the same element both survive.
3. **No cycles.** Concurrent moves can never make an element its own ancestor.
4. **No central authority.** Merging needs no server to decide order.

## Built on Yrs

The first implementation of Xmesh is a thin layer on **[Yrs](/discussion/prior-art/#yata-yjs-and-yrs)**, the Rust port of Yjs. Yrs already provides the hard, well-tested parts: YATA ordering for sequences and text, maps, state vectors, a compact binary update format, and snapshots. Xmesh adds what an XML tree needs on top:

- a **schema** that maps XML elements onto Yrs maps and text
- **cycle-safe tree moves**, which Yrs doesn't have
- **XML Patch translation**, from UI actions to Yrs operations
- **canonical XML output**, for hashing and rendering

Xmesh stays a pure core: no networking, no files, no clocks. See [decision 13](/discussion/decisions/#13-xmesh-v1-is-yrs-plus-a-tree-layer).

## Data model

<Diagram name="09-class-model" alt="Class diagram: an Xmesh document is a Yrs document holding a map of nodes keyed by the ID of the operation that created them; each node has a kind, a namespaced name, an edge map from parent to counter and position, an attribute map, a deleted flag, and text content for text nodes; client IDs are bound to authors' public keys; a session has a parent and a fork snapshot." />

<span class="status status--decided">decided</span> ([decision 20](/discussion/decisions/#20-the-tree-schema-and-a-deterministic-move-algorithm))

The document is a **map of nodes, keyed by node ID**, not a nested Yrs XML fragment. Each node holds:

| Field | Yrs type | Purpose |
| --- | --- | --- |
| `kind` | string | `element` or `text`. Text nodes give SVG's `<text>` and `<tspan>` their mixed content. |
| `name` | string | Elements only: the expanded name, namespace URI plus local name, such as `{http://www.w3.org/2000/svg}circle` |
| `edges` | map: parent ID → (counter, position) | Every parent the node has had, each with the position it was given there. The highest counter is its current parent and position (see moves, below). |
| `attrs` | map | Elements only: attributes by expanded name, such as `fill` or `{http://www.inkscape.org/namespaces/inkscape}label` |
| `deleted` | boolean | A tombstone. See deletion, below. |
| `content` | text | Text nodes only: the characters |

- **Node IDs need no coordination.** A node's ID is the Yrs ID of the operation that created it: client ID plus counter. Client IDs are [fresh per session and connection](/spec/identity/#signing-only-at-identity-steps), so IDs never collide.
- **Namespaces are stored expanded.** Prefixes such as `inkscape:`, `sodipodi:` and `xlink:` are chosen only when writing XML out, by the canonical form.
- **Genesis is one fixed update.** Every document starts from the same initial update that creates the root, identical byte for byte everywhere, so two peers can never create two different roots.

### Deletion

Deleting a node sets its `deleted` flag. The node and everything under it disappear from the materialised tree, but stay in the document:

- **Edits inside a deleted node still merge.** They are hidden with it.
- **Undeleting clears the flag**, and the node comes back with everything that was done inside it meanwhile. Undo relies on this.
- **A move into a deleted node** is hidden too, until the node is undeleted.

## Ordering

Within text, Yrs orders concurrent insertions with **YATA** (Yet Another Transformation Approach). Each insertion remembers the neighbours it went between, and ties are broken by client ID. Deleted characters become tombstones, so later insertions can still find their place.

Among siblings, order comes from each node's **fractional index**: a sortable key that can always fit a new key between two others. The position lives on the node's current edge, so its parent and its place among that parent's children always come from the same move. Reordering within the same parent is a move to the same parent with a new position.

Two people inserting at the same spot at the same time could generate the same key, so **every key ends with the client ID of the peer that made it**. Keys are then always distinct, and ties break the same way everywhere.

## Immortal parents

An XML element is never replaced, only updated:

- its **attributes** live in a map, last-writer-wins per key
- its **children** point to it, rather than living inside it

Setting `@fill="blue"` updates one map entry. The `<circle>` keeps its ID, so a concurrent edit to the same circle still has something to land on. Replacing whole nodes would orphan concurrent edits; immortal parents prevent that.

<Aside type="caution" title="Why not Yrs's own XML types?">
Yrs has XML element and fragment types, but in them a move is a delete plus an insert: the element gets a new identity, and concurrent edits to it are lost. A flat node map with parent pointers keeps identity through moves.
</Aside>

## Moves without cycles

Moving an element changes its parent. If Alice moves group A into group B while Bob moves B into A, a naive merge creates a cycle. Xmesh uses **Evan Wallace's mutable tree algorithm** ([prior art](/discussion/prior-art/#cycle-safe-tree-moves)):

<Diagram name="10-activity-move" alt="Activity: to move a node, write the new parent into its edge map with a counter one above its current maximum and the new position. To read the tree, each node's best edge is the highest counter, then the lowest parent ID; nodes that reach the root are rooted; nodes caught in cycles are rooted in ascending node ID order at their best edge to an already-rooted parent; children are ordered by position and deleted nodes are hidden." />

- **A move is a map write.** The node's edge map gets the new parent, with a counter one higher than any it already has, and the position it's given there. Old entries stay.
- **Reading the tree resolves cycles deterministically**, by the algorithm below.
- **Every peer agrees**, because they all apply the same rule to the same converged maps. Stored data is never rewritten, so peers never fight over it.

### Reading the tree

<span class="status status--decided">decided</span>

Node IDs compare by client ID, then counter. Edges compare by counter, highest first, then by parent node ID, lowest first.

1. The root (from genesis) is **rooted**.
2. Give every other node its **preferred edge**: its best edge by the order above.
3. Follow preferred edges. Every node whose chain reaches the root is **rooted**, at its preferred edge.
4. Take the nodes that aren't rooted. They are caught in cycles. Go through them in **ascending node ID order**. For each one, take its best edge whose parent is now rooted. If it has one, it is rooted there; then root any nodes whose preferred edge leads to it.
5. Repeat step 4 until every node is rooted. This always ends, because every node's first edge, from when it was created, points to a parent that existed before it, so those edges lead back to the root.
6. Within each parent, order children by the position on their chosen edge.
7. Hide deleted nodes and everything under them.

The [`yrs_tree`](/discussion/prior-art/#cycle-safe-tree-moves) crate implements Wallace's algorithm on Yrs. It will be spiked against this algorithm and the test vectors, and adopted only if it gives exactly the same trees.

## Clocks and state vectors

- Every operation is stamped with an **ID**: the client that made it, plus that client's own counter.
- Every peer keeps a **state vector**: for each client, the highest counter it has integrated.
- Two peers sync by exchanging state vectors. Each sends the operations the other is missing.

Yrs provides all three.

### Snapshots name points in history

<span class="status status--decided">decided</span>

A state vector says how far a peer has got, but it doesn't pin a state. In Yrs, deleting something doesn't use a clock value: deletions are recorded in a separate **delete set**. So two peers with the same state vector can still differ by what they've deleted.

A point in history is therefore named by a **snapshot**: a state vector plus a delete set, as Yrs defines it.

- **A [session](/spec/sessions/) records the full snapshot it was forked at.** Rebuilding a fork from it gives exactly the state at the fork, even if content was deleted afterwards.
- **Addresses and ETags carry a short hash of a snapshot.** `@{snapshot}` in a URL is that hash, and the host keeps the snapshot it stands for. Because the hash covers deletions, deleting a shape changes the ETag, so a no-JS browser polling with `If-None-Match` sees it.
- **Snapshots need Yrs's garbage collection off**, so deleted content is kept. This is the rule from the start.

<Aside type="note" title="Terminology">
Per-client counters stamp operations, and state vectors describe what a peer has seen. Neither is a vector clock in the usual sense.
</Aside>

## Canonical form v0

<span class="status status--decided">decided</span> as a starting point ([decision 21](/discussion/decisions/#21-canonical-form-v0-and-one-wire-format-to-start))

Convergence is checked by comparing the SHA-256 of each peer's XML, so every implementation must write exactly the same bytes. Full W3C Canonical XML is built for XML signatures and is more than this needs. **Xmesh canonical form v0** is:

- **UTF-8**, with no XML declaration.
- **Deleted nodes left out**, with everything under them.
- **Attributes sorted** by expanded name: namespace URI, then local name.
- **Fixed prefixes** for known namespaces: SVG as the default namespace, and `inkscape:`, `sodipodi:` and `xlink:`. Any other namespace gets `ns1`, `ns2` and so on, in order of first use.
- **No whitespace** except what's inside text nodes.
- **Minimal escaping**: `&` and `<` in text; `&`, `<` and `"` in attribute values, which are always double-quoted.

The version is part of the form, so a later change never leaves doubt about which rules produced a hash.

## The patch language

UI actions are expressed as **XML Patch** operations, an import and export format only, never sent between peers, (RFC 5261: `add`, `replace`, `remove`, addressed by XPath) before they reach the engine. Xmesh translates each patch into Yrs operations that refer to node IDs, not positions, because XPath positions shift under concurrent edits.

RFC 7351 registers the `application/xml-patch+xml` media type for these documents. The patch operations themselves are defined in RFC 5261.

## Still open

- **History and garbage collection.** Garbage collection stays off, so deleted content is kept. How much history to keep is part of the [roadmap](/build/milestones/#roadmap).
- **Snapshot hashes:** which hash, how short it can safely be, and how it's written after `@`.
- **Provenance beyond the host:** whether clients should occasionally sign a hash chain of their own operations (see [Identity and access](/spec/identity/#still-open)).
