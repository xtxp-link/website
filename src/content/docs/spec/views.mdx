Collaborators need to see edits **before they merge**. Neither the original design handover nor most CRDT libraries cover this, so it is a core requirement here.

## The views

**Onion skin**
: A translucent overlay of another state drawn over the current one: a session over its parent, a paused queue over the live document, or another connection's session that hasn't been merged yet. Every session can be shown as an onion skin.

**Redline**
: A per-author tracked-changes view. For a session, it is the set of operations that a merge would replay, coloured by who made them.

**Paused queue**
: A local session whose automatic merge is switched off. Its edits show as a translucent preview over the live document, and releasing it is an ordinary [merge](/spec/sessions/#fork-preview-merge).

**Session preview**
: Any session rendered on its own or over its parent, for review before merging.

**Prior art:** onion skinning comes from traditional animation, and the redline from word processors' tracked changes ([prior art](/discussion/prior-art/#seeing-edits-before-they-merge)).

## Who renders them

All views belong to the **application layer on a muppet**. They are ephemeral changes to the displayed tree and never change the state of the session being viewed. An application receives a screen from a muppet and decides how to render it.

That holds wherever an application drives a muppet:

- **in Inkscape**, the Inkscape application draws the views on the canvas (bound to the muppet running on the user's machine or a server)
- **in the browser**, the server-side application renders the views as HTML and SVG; the browser application shows the rendered result. *Future:* the muppet may move to the browser (Wasm or native), and the browser application renders its screens directly.
- **on the server for a no-JS browser**, the server-side application renders the views as plain SVG layers and HTML

Because server-side rendering is an application on a server-side muppet, the no-JS view and the native view come from the same muppet library and application code.

## What the engine must provide

- **Authorship on every operation**, kept after merging, so a redline can say who changed what.
- **A state per session**, so a preview has something to overlay.
- **Cheap diffs between two states**, so a redline can be computed on demand.

## Still open

- Should the onion skin show *live* in-flight edits from other people, explicit *suggestions* that need accepting (like tracked changes in a word processor), or both?
- How redline colours map to authors in a room with many participants.
