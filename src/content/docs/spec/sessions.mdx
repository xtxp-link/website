## One mechanism for undo, proposals and previews

A **session** is a fork of a document's history at a point given by a state vector: a branch, in git's terms. Sessions are meant to be cheap enough to make one per person, per proposal or per visit. That one idea covers several features:

- **A personal session** is one user's own state, which may never leave that user's own MUPPET: a private scratch copy, a draft, or the state an ordinary web session would keep today. See [use cases](/overview/use-cases/#user-sessions).
- **Undo** forks a session from an earlier point, so history is never thrown away.
- **A proposed edit** is a session that hasn't been merged yet.
- **A preview** draws a session over its parent.
- **A paused queue** is a local session whose automatic merge is switched off. Releasing it is an ordinary merge.
- **Infinite, branchable undo** falls out of keeping every session's operations. How that history is stored long-term is on the [roadmap](/build/milestones/#roadmap).

A session is **identified by where it lives**: its address, `{host}/{path}@{name}`. There are no generated IDs. Each session also records its **parent** (another session's address) and the **state vector at the fork**.

### Naming a session

The creator names a session, and the name must be unique on its host. Because the name is an address:

- **Asking for a name that already exists opens that session**, like checking out an existing branch in git, subject to its read and write grants.
- **Creating a new fork on a name that's taken is rejected**, and so is asking for a session you have no access to.

Nobody can overwrite or hijack a session by naming, and two people who pick the same name for the same thing end up working in the same session.

**Prior art:** cheap sessions, merges as replays and an authoritative upstream all come from git ([prior art](/discussion/prior-art/#git)). The undo side builds on Inkscape's transaction-based undo stack ([prior art](/discussion/prior-art/#inkscapes-undo-stack)). Access to sessions is covered in [Identity and access](/spec/identity/#access-is-granted-by-key).

## Undo in practice

<span class="status status--draft">draft</span>

Two kinds of undo meet here:

- **Personal undo (Ctrl+Z)** reverses *your own* recent actions with inverse operations, leaving collaborators' edits alone. One step is one action, grouped the way [Inkscape groups an action into a transaction](/discussion/prior-art/#inkscapes-undo-stack), including merging small repeated steps such as a drag or a spin button.
- **History undo** goes back to an earlier state of the whole document. That's a session from an earlier state vector.

Where they differ from Inkscape: in Inkscape, undoing and then making a new edit clears the redo stack, and the undone work is lost. In XTXP, the undone work is still in the document's history, so it can be reached again through a session from before the undo.

## Hosting a session

Any MUPPET can **host** a session. A host holds the session's Xmesh document like any other MUPPET, and also:

- **admits** operations against the session's [grants](/spec/identity/#access-is-granted-by-key), in arrival order
- **routes** admitted operations to everyone subscribed to the session
- **persists** the session and hands new clients its full state (see below)

On a server, each hosted session runs headless, with no views and no user of its own, as a lightweight actor: an async task that owns one session and talks to the rest only by messages. Actors are cheap enough to spawn one per proposed edit or undo fork, and a failure in one session stays contained.

### Sessions on other hosts, and trust between them

<span class="status status--draft">draft</span>

Every host holds **its own sessions**. A session never lives on two hosts at once: a copy elsewhere is a different session, with its own address, in the way every git clone has its own sessions.

<Diagram name="16-session-trust" alt="Sessions on different hosts linked by trust: a session on an Inkscape instance on a local network and a session on an edge host both trust and are trusted by main on the server, so changes merge automatically in both directions; a paused session on the laptop has its automatic merge switched off." />

- **Only a session's own host admits edits to it**, in its own arrival order.
- **Trust between sessions drives automatic merging.** If session A trusts session B, B's changes merge into A as they arrive, by ordinary state-vector sync. Trust can run one way or both ways, so a studio's session on its local network and `main` on a server can keep each other up to date.
- **A paused queue** is a session whose automatic merge is switched off until it's released.
- **Merges converge in any direction.** CRDT merges are commutative and idempotent, so two sessions that trust each other can't loop or diverge.

For example, `xtxp.example.org/drawing@main` can be forked onto a laptop as `my-laptop.lan/drawing@sketch`, with the fork trusting `main` so it stays current, and `main` trusting the fork only once it's ready.

### Storage: toolchain first

The Yrs ecosystem already has the building blocks a host needs:

- **A full state as one update.** Yrs can encode a whole document as a single update, so a new client loads one compact blob instead of replaying history.
- **Append, then compact.** Storing each incoming update and periodically merging them into one is the usual pattern for persisting Yjs documents.

XTXP starts with those, and [y-sweet](/discussion/prior-art/#y-sweet) already implements them for Yjs documents. A dedicated **ledger** (a chronological patch log in cold storage) and **keyframes** (hot snapshots tuned for instant loading) are on the [roadmap](/build/milestones/#roadmap), to be built only if the toolchain's own approach falls short.

## Fork, preview, merge

<Diagram name="07-seq-session" alt="Sequence: an author forks main at a state vector, a host for the session is spawned, the author sends ops to it, a reviewer views onion skin and redline rendered by the server MUPPET, accepts, and main replays the session ops and fans them out." />

**Merging is mechanical.** CRDT operations commute, so merging a session means applying its updates to the parent. Nobody has to resolve conflicts by hand, and the **redline** is exactly the set of operations being applied, grouped by author.

On Yrs: a **fork** is a new document seeded with the parent's state at the fork's state vector (a snapshot, which needs Yrs's garbage collection off). A **merge** encodes the session's updates since that state vector and applies them to the parent.

## Still open

- How long abandoned sessions stay loaded before they're only kept in storage.
- Permissions: who may fork, who may merge into which session.
- Whether a merge records itself as an operation, so it can be undone by branching from before it.
- Exactly how personal undo groups operations, and how far back it reaches once collaborators have built on your changes.
