## The parts

| Part | Role | Status |
| --- | --- | --- |
| **XTXP** | The specification. *The Math*: CRDT rules, clocks, patch structures, cycle-free moves. *The Wire*: stanza framing, handshakes, branch routing. The language-agnostic contract every node obeys. | <span class="status status--draft">draft</span> |
| **Xmesh** | The engine. Resolves concurrent patch streams. A pure, hexagonal C++20 core, the only implementation for now. A pure Elixir port is deferred to a later spike. | <span class="status status--decided">decided</span> |
| **MUPPET** | Multi User Progressive Patch Execution Tree: client-side Xmesh, and the application layer. Turns local edits into outbound XTXP payloads, applies incoming patches to the local XML tree, and owns every view: the vector canvas, spatial chat and comments, paused queues, onion skin and branch previews, none of which change document state. | <span class="status status--decided">decided</span> |
| **Erlang Trackers** | The routing layer. One lightweight Erlang process per branch, holding that branch's history, hot keyframes and presence, and routing patches between nodes. | <span class="status status--decided">decided</span> |

## A pure, hexagonal core

Xmesh is the hexagon's centre: pure state transformations, with no networking, no file access, no clocks and no threads. Everything that touches the world is an adapter around it:

- **Inkscape:** the core linked into the fork
- **Browser:** the core compiled to Wasm
- **Server:** the core as a standalone process, which the server-side MUPPET uses and Erlang trackers drive through a Port
- **Tests:** the core driven directly by the vector harness

Keeping the core pure is what lets one C++ codebase serve every one of these.

## The split that matters

There is **no central authority**. "Canonical state" means the state every peer converges to, not a state a server announces.

- **MUPPETs execute and render.** Every client runs Xmesh, so desktop clients work offline and merge on reconnect. A MUPPET can run in three places: the Inkscape fork, the browser (Wasm), and the server, on behalf of a browser with no JavaScript.
- **Trackers hold history.** Each branch is a process with its own ledger and keyframes. Trackers serve new clients a recent keyframe instead of replaying the whole history.
- **XTXP is node to node.** It connects MUPPET to MUPPET, MUPPET to tracker, and tracker to tracker. It is not a client–server API.

Because rendering is just a MUPPET running somewhere, the no-JS view and the Inkscape view come from the same code and can't drift apart.

## Transport

XTXP is a small sync protocol that doesn't care about transport. Its main binding is **WebSocket**, for raw speed, which trackers speak directly from the BEAM. Browsers without JavaScript use **HTTP** through a server-side MUPPET. Mobile and chat clients reach a tracker through an **XMPP bridge**, which keeps push and store-and-forward for phones. Reconnecting is a state-vector exchange built into XTXP. See [The Wire](/spec/wire/).

Identity is a **public key**, and access is granted by key. See [Identity and access](/spec/identity/).
