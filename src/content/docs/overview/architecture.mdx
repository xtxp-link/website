## The parts

| Part | Role | Status |
| --- | --- | --- |
| **XTXP** | The specification. *The Math*: CRDT rules, clocks, patch structures, cycle-free moves. *The Wire*: sync messages, handshakes, branch routing. The language-agnostic contract every node obeys. | <span class="status status--draft">draft</span> |
| **Xmesh** | The engine. Resolves concurrent edits. A thin, pure Rust layer on Yrs that adds an XML tree schema, cycle-safe moves and XML Patch translation. A native C++ rewrite is a possible later spike. | <span class="status status--decided">decided</span> |
| **MUPPET** | Multi User Progressive Patch Execution Tree: client-side Xmesh, and the application layer. Turns local edits into outbound XTXP payloads, applies incoming patches to the local XML tree, and owns every view: the vector canvas, spatial chat and comments, paused queues, onion skin and branch previews, none of which change document state. A MUPPET can also run headless and **host** a branch: admitting edits against its grants, routing them and storing the branch. | <span class="status status--decided">decided</span> |

## A pure, hexagonal core

Xmesh is the hexagon's centre: pure state transformations, with no networking, no file access, no clocks and no threads. It is a Rust crate built on Yrs, and every integration is an adapter around it:

- **Inkscape:** linked into the fork through a C interface, the way `yffi` exposes Yrs to C
- **Browser:** compiled to Wasm
- **Server MUPPET:** used natively from Rust
- **Hosting MUPPETs:** used directly, in Rust
- **Tests:** driven directly by the vector harness

Keeping the core pure is what lets one Rust codebase serve every one of these. See [decision 13](/discussion/decisions/#13-xmesh-v1-is-yrs-plus-a-tree-layer).

## The split that matters

There is **no central authority**. "Canonical state" means the state every peer converges to, not a state a server announces.

- **MUPPETs execute and render.** Every client runs Xmesh, so desktop clients work offline and merge on reconnect. A MUPPET can run in the Inkscape fork, in the browser (Wasm), on a server for a browser with no JavaScript, or headless as a host.
- **Any MUPPET can host a branch.** A host holds the branch like any MUPPET and adds admission, routing and storage; on a server it runs headless, with no views and no user of its own. A branch can have several hosts, upstreaming to each other. New clients load its full state as one compact update instead of replaying history. A dedicated ledger and keyframes are on the [roadmap](/build/milestones/#roadmap).
- **XTXP is node to node.** It connects any MUPPET to any other, hosts included. It is not a client–server API.

Because rendering is just a MUPPET running somewhere, the no-JS view and the Inkscape view come from the same code and can't drift apart.

## Transport

XTXP is a small sync protocol that doesn't care about transport. Its main binding is **WebSocket**, for raw speed, which hosts serve directly. Browsers without JavaScript use **HTTP** through a server-side MUPPET. Mobile and chat clients reach a host through an **XMPP bridge**, which keeps push and store-and-forward for phones. Reconnecting is a state-vector exchange built into XTXP. See [The Wire](/spec/wire/).

Identity is a **public key**, and access is granted by key. See [Identity and access](/spec/identity/).
